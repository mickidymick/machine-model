# A measured machine descriptor

**What a leadership-class machine says about itself, what it actually does, and
the gap between them.**

Jeffrey Z. McMichael · University of Tennessee, Knoxville · ORNL
2026-09-09

---

## 1. The problem

Getting an application to run well on a machine like Frontier is a
configuration problem before it is a programming problem. Someone has to choose
a rank and thread geometry, an affinity and binding policy, a page size, where
buffers live relative to the device that reads them, and how data reaches
storage. These choices routinely separate a run from one twice as fast, and
none of them are properties of the source code alone.

**What we normally have to work from, to make those choices, is a *declared*
description of the machine:**

| Source | What it gives |
|---|---|
| Vendor node diagram | core count, device count, block layout |
| Facility spec sheet | peak injection bandwidth, memory capacity |
| ACPI SLIT, via `numactl -H` or `hwloc_distances_get` | a scalar "distance" per NUMA pair |
| sysfs, `/proc`, `lscpu` | cache sizes, page settings, allowed CPU masks |
| Facility user guide | recommended flags, scheduler options |

This material has two properties that matter. First, **it is overwhelmingly
structural**: it says what exists and how it is wired, not what anything costs.
Second, **where it does state a cost, that cost is a firmware constant that
nobody measured** — the SLIT table is authored by the platform vendor, not
sampled from the platform.

That is the gap this work addresses. The claim is not that the declared
description is useless; it is the necessary skeleton. The claim is that a
configuration decision needs a cost model, the declared description does not
carry one, and where it appears to, the number is frequently wrong.

## 2. The instrument gap: why the benchmarks had to be built

The obvious way to measure a node's memory hierarchy is the Intel Memory
Latency Checker, which is what most people reach for. **MLC does not run on
Frontier.** It depends on Intel uncore behaviour for its loaded-latency sweep
and has no concept of a GPU or of high-bandwidth memory, so on an AMD EPYC node
with four MI250X accelerators it has nothing to say.

So the MLC feature set was rebuilt out of AMD- and HPC-native pieces, using
stock tools where they existed and custom code only where a real gap remained:

| MLC feature | Rebuilt as | Status |
|---|---|---|
| `--latency_matrix` | `ptrchase` + `01_cpu_matrix.sh` | custom, random dependent chase |
| cache/memory curve | `ptrchase --curve` | custom |
| `--loaded_latency` | `loaded_lat` | custom, injection-delay sweep |
| `--bandwidth_matrix` | `bwmatrix` | custom |
| *(no equivalent)* GPU HBM/cache curve | `gpu_ptrchase --curve` | custom, HIP |
| *(no equivalent)* GCD ↔ peer ↔ host matrix | `gpu_ptrchase --matrix` | custom, HIP |
| *(no equivalent)* inter-node | OSU Micro-Benchmarks 7.4 | stock |
| *(no equivalent)* GPU bandwidth | `rocm-bandwidth-test` | stock |
| *(no equivalent)* SMT response | `smt_probe` | custom, three kernels |
| *(no equivalent)* fabric locality | Slurm topology + OSU pair census | stock + custom analysis |
| *(no equivalent)* storage tiers | `20_storage_locate.sh`, `storage.sbatch` | custom |

Three methodological commitments make the output trustworthy, and each of them
came from being burned first:

- **Every custom tool was validated against real MLC on a known Intel machine
  before it was believed on Frontier**, agreeing within about one percent on
  the measurements the two have in common. Where they disagree by design — these
  tools chase a random dependent cycle, MLC's latency matrix is sequential — the
  difference is stated and quantified rather than papered over.
- **A noise floor was established before any claim was made.** CPU latency
  ±1.2 ns, CPU bandwidth ±289 MB/s, inter-node bandwidth ±10.3 MB/s, GPU
  latency ±37.6 ns (~8%, which is what makes one result below a null rather
  than a finding).
- **The manipulation is verified, not assumed.** An experiment that never ran
  produces output indistinguishable from one that found nothing. Several early
  results were false nulls — a module that silently failed to take effect, a
  load generator that died at startup, a job step that silently serialised —
  and every probe now aborts loudly when a precondition fails and sanity-checks
  its own output against a physical ceiling.

## 3. The idea

The artifact is **a versioned description of one node type that records the
declared and the measured description side by side, and treats their
disagreements as first-class records rather than corrections.**

- A portable **registry** owns the questions — twenty of them at v0.6 — and the
  rule for deciding each. It is machine-independent.
- A per-machine **descriptor** holds the answers: for each claim, what the
  machine declares, what measurement returned, and a verdict.
- Verdicts are `confirmed`, `misleading`, `contradicted`, `undeclared`,
  `unfalsifiable_here`, and `not_applicable`.

Four design decisions do most of the work:

**Declared values are never overwritten.** Overwriting destroys the evidence
that anything reading `numa_distance()` is getting a wrong answer. The
disagreement *is* the product.

**`confirmed` is a result, not a non-event.** Without confirmations,
"firmware is unreliable" is an anecdote. With them it becomes specific: these
four survive, these three do not, and here is the profile.

**Every measured quantity carries its regime.** A number is rendered with
`measured_under`, `not_measured`, and `mechanism` *before* the value. A cost
curve is meaningless outside the conditions that produced it, and a structured
field naming one regime variable implicitly asserts there are no others — a
defect we found by having a reader act on it.

**Declaration fidelity is the comparable quantity across machines.** Not the
individual numbers, which are machine-specific, but *what fraction of what this
machine says about itself survives measurement.* Frontier: **33%** (4 of 12
resolved claims). corsys4: **50%** (3 of 6).

## 4. What the characterization found on Frontier

Node: 1× AMD EPYC 7A53 (64 cores, 2 HWT, NPS4), 512 GB DDR4, 4× MI250X (8 GCDs),
4× Slingshot-11 NIC. Characterized 2026-07-19, extended 2026-08-10 and 08-18/19.

### 4.1 Where the declared description is wrong

**The NUMA distance matrix is contradicted — and this is the central result.**
The ACPI SLIT reports every remote hop as equidistant, `12` against a local
`10`: all four domains mutually equidistant, every remote access costing 1.2×.
That is what any tool reading the standard interface believes. Measurement
resolves **three distinct tiers**:

| | pairs | latency (ns) | bandwidth (MB/s) |
|---|---|---|---|
| local | — | 101.5 | 44582 |
| near | 0↔1, 2↔3 | 107.9 – 108.9 | 43750 – 43962 |
| mid | 0↔2, 1↔3 | 115.8 – 116.1 | 43020 – 43219 |
| far | 1↔2, 0↔3 | 119.2 – 120.0 | 42397 – 42841 |

Reproduced independently by two separately written tools, and by an order of
magnitude more than the ±1.2 ns noise floor. Two corollaries matter as much as
the finding:

- **The declared 1.200× exceeds every measured hop.** So the failure is not
  "firmware understates cost", which would be a calibration error better numbers
  could fix. The scalar is roughly right *on average* and **erases the
  structure**. One number per pair cannot hold three tiers.
- **The effect is ~3.7× stronger in latency than in bandwidth** — an 18.2%
  span across tiers versus 4.9%. A bandwidth-only benchmark reports these
  domains as interchangeable and sees no topology at all. *Which instrument you
  choose determines whether the structure is visible.*

**Direction is not representable at all.** Measured on one pair, 2→3 costs
110.8 ns and 3→2 costs 106.9 ns. A scalar distance has one slot per pair, so
whatever causes the asymmetry, the declared data model has nowhere to put it.

**The node has 56 usable cores, not the 64 on the diagram.** Eight are reserved
for the OS, one per L3 region. hwloc reports this correctly (112 allowed PUs of
128); the vendor diagram does not, and the two declared sources disagree with
each other.

**The node exposes 8 schedulable GCDs, not 4 GPUs.** The MI250X presents two
Graphics Compute Dies, and the GCD is the unit ROCm and Slurm actually schedule.

**Both normal paths to huge pages fail silently.** THP is set to `never` and the
hugetlb pool holds 4 pages, 0 free. The allocation succeeds, `madvise` returns
success, and the backing is 4K. Nothing errors.

**The NIC shortfall is a placement artifact, not a hardware limit.** The spec
sheet declares 100 GB/s injection per node; a natural single-pair benchmark
returns 22.6 GB/s and reads as a 4× shortfall. Spreading ranks across NUMA
domains, one per NIC:

    1 pair   22673 MB/s     1.00x
    2 pairs  45103 MB/s     1.99x
    4 pairs  90262 MB/s     3.98x     = 90.3 GB/s, ~90% of declared

Perfectly linear, and the 4-pair aggregate divided by four matches the 1-pair
number within 0.5%. The declared number is reachable; reaching it is a
placement decision no document tells you to make.

**`df` is wrong in both directions at once.** On a compute node it shows ~252 G
each of `/tmp`, `/dev/shm` and `/rootfs.rw` — all tmpfs, i.e. **RAM**, so a job
writing bulk output there OOMs. Meanwhile 3.4 TB of real node-local NVMe exists
on every node and is invisible unless the job asks for `-C nvme`. Both paths a
user reaches for by habit are wrong for bulk I/O.

### 4.2 Where nothing is declared and measurement is the only source

Six of twelve resolved claims have **no declared source at all**. There is no
document, anywhere, that answers them.

**Page-size penalty — a curve, not a constant, that peaks while data is still
cache-resident.** Huge versus 4K pages under random dependent access:

| working set | huge | 4K | penalty |
|---|---|---|---|
| ≤ 256 KB | — | — | none (TLB covers it) |
| 512 KB | 3.6 | 5.4 ns | 1.5× |
| 16 MB | 13.1 | 17.5 ns | 1.3× |
| **32 MB** | **13.3** | **32.2 ns** | **2.4× — peak** |
| 64 MB – 1 GB | 58–89 | 67–103 ns | settles to a constant offset |

The peak is at 32 MB because the working set still fits in a 32 MB L3 region
but needs 8192 page-table entries at 4K, far past TLB reach — so every access
pays a page walk that itself goes to memory. **The penalty is largest where the
data is cheapest to reach.** It exists only where the working set exceeds TLB
reach *and* the access pattern defeats prefetch; a contiguous streaming kernel
amortises the walk across a whole page and sees nothing.

**Loaded-latency knee.** Peak 44521 MB/s at 832 ns; the knee at 43752 MB/s and
234 ns. **98% of peak bandwidth is available at 28% of the latency**, which is
the operating point a latency-sensitive code wants and no document states.

**Host-versus-device buffers for inter-node transfer.** Device-resident buffers
are 5.48% faster in bandwidth and 5.90% in latency at 4 MiB. The effect is
small but far outside the noise: 23877 against 22636 MB/s, a 1241 MB/s
difference against across-pass spreads of 8.1 and 10.3 MB/s. And they *lose*
below the crossover, which sits at 16 KB for bandwidth and 256 KB for latency,
with a 12–14% penalty under 64 KB.

**SMT response, and the rule is not the obvious one.** Three kernels, each
purely one thing: `chase` (memory-latency-bound) **+69.7%**, `fma` (FPU-latency
bound) **+78.2%**, `stream` (bandwidth-saturated) **−5.0%**. The prediction was
that the FPU kernel would gain least, because the FPU issue width is shared;
it gained most, because four dependent chains under-saturate a 2/cycle issue
width. **The rule is latency-bound versus throughput-bound, not memory versus
compute.**

**Collective cost is a surface, not a scalar.** From 8 to 128 ranks, allreduce
at 1 MiB grows **1.6×** (760.5 → 1200.6 µs) while alltoall at 64 KiB grows
**26.3×** (45.1 → 1186.1 µs). Both are large-message collectives on the same
fabric at the same rank counts, and they scale in different *kinds* — allreduce
moves a nearly fixed volume per rank however many peers exist, while alltoall's
message count grows as n². No single number and no single curve describes it.

**Storage bands, measured against Orion's own declared layout.** `$MEMBERWORK`
and `$PROJWORK` share a 7-component Progressive File Layout that silently
migrates a file from the `performance` pool to `capacity` at 8 MiB. The
declared 256 KiB Data-on-MDT boundary **is** observable — an 8.1× step. The
declared 8 MiB pool change is **not**. And node-local NVMe versus Lustre
**crosses over** between 64 MiB and 256 MiB: 3.91× faster locally at 8 MiB,
0.54× at 1 GiB. "Node-local is faster" is wrong at checkpoint sizes.

### 4.3 Two nulls that are results

**GPU-to-host NUMA affinity is `unfalsifiable_here`.** Eight GCD rows, a rule
that a row votes only when its across-domain range exceeds 3× its worst
across-pass spread; **0 of 8 cleared it**. If the penalty exists it is smaller
than the 8% run-to-run GPU latency variance. Reported as a bound, not a claim.

**The cross-switch fabric class is uniform.** A 240-pair census returned 3.68 µs
at 8 B (±0.7%) and 21975 MB/s at 1 MiB (±0.8%) — one tight mode, with
switch-name families indistinguishable. This tested *our own* hypothesis that
Slurm's two-level switch tree is structurally insufficient for a dragonfly the
way a scalar SLIT is for asymmetric NUMA. At the scale sampled, it is not. The
hypothesis was falsified, and the verdict is `confirmed` on a declared model —
the category that makes the contradicted claims credible.

## 5. The second machine

corsys4 — Xeon Gold 6246R, 192 GB DDR4 plus 730 GB of cpuless Optane — was
described with the same schema. The tempting summary is *both firmwares
understate crossing cost.* **It is false**, and the real result is stronger:

| | declared | measured | failure mode |
|---|---|---|---|
| Frontier | 1.200× every remote hop | 1.063 – 1.182×, three tiers | scalar ≈ right on average, **erases structure** |
| corsys4 | 1.700× | 2.35× latency / 2.87× bandwidth | no structure to erase, **scalar simply wrong** |

**Two machines, two genuinely different failure modes, one data model.** On
corsys4 the two metrics also disagree with *each other* by 22%, so no single
scalar could be right for both.

And the page-size penalty has **two peaks on corsys4** — 2.72× at 1 MB while
data is L2-resident, 1.74× at 32 MB while L3-resident — against Frontier's one.
Same mechanism, TLB reach failing while data is still cached, at different sizes
because the cache and TLB geometries differ. That is the best single argument in
the project for carrying curves rather than scalars: the same code, on two
machines, produces a differently *shaped* answer.

## 6. What it is for

The descriptor is the machine half of a decision that needs machine × application.
The intended primary consumer is an LLM given the application source, because it
is the only consumer that already holds the other half. That pairing is the
subject of a separate controlled evaluation, currently in progress; the first
completed experiment shows that supplying the measured description improves what
a model *knows* about the platform (13 of 14 checkable questions, against 7 of 14
for both a vendor-documentation baseline and a web-search baseline, which scored
identically to each other). **Whether that knowledge produces better
configurations is the open question, and it is not yet answered.**

The characterization stands on its own regardless of how that lands. It also
supplies the reference ZeroSum (Huck & Malony, SC-W 2023) explicitly left out:
they laid out six phases and did not build phase 2, *evaluate the configuration
to detect misconfigurations*, because it "would require a comparison to a known
'good' configuration for this platform."

## 7. Status

- Registry **v0.6**, 20 claims, portable across machines.
- Two machines described: Frontier compute (33% fidelity, 4 of 12 resolved) and
  corsys4 (50%, 3 of 6). Eleven documented pitfalls.
- Probe harness complete for CPU, GPU, inter-node, SMT, collectives, fabric and
  storage; producer (measurement) and consumer (rendering) deliberately split so
  a domain scientist never has to build a probe.
- Immediate next steps: extend to additional leadership-class machines — a third
  machine where the SLIT is *accurate* would be the single most informative data
  point available, since it would make the error a vendor choice rather than a
  norm — and complete the configuration half of the evaluation.
