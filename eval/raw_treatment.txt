This is a closed-book reasoning task over the briefing you provided, so I'm answering directly from it rather than running anything. Where the document explicitly hedges or doesn't cover something, I've said so instead of inventing a number.

Q1: 56 usable cores; srun -c 56 is the maximum valid value. One core per L3 group is OS-reserved (logical indices 0, 8, 16, 24, 32, 40, 48, 56), which hwloc confirms as 112 allowed PUs of 128 topology PUs. The node physically has 64 cores, but -c 64 is rejected outright — trust hwloc/lstopo, not the vendor node diagram.

Q2: They are not equivalent (the ACPI SLIT says they are, and measurement contradicts that). Cheapest to most expensive by measured latency: 0‑1 (107.9 ns) < 2‑3 (108.9) < 0‑2 (115.8) < 1‑3 (116.1) < 1‑2 (119.2) < 0‑3 (120.0). This is a three-tier structure — near {0‑1, 2‑3}, mid {0‑2, 1‑3}, far {1‑2, 0‑3} — corroborated by both a pointer-chase and a streaming tool with identical rank ordering.

Q3: No — crossing cost is directional, though this is stated at medium confidence and only one pair was measured both ways. For pair 2/3, 3→2 is better in both metrics (106.9 ns / 44,263 MB/s) than 2→3 (110.8 ns / 43,662 MB/s), a 3.9 ns gap against a 1.2 ns floor. A single scalar per pair is structurally insufficient to express this, but the briefing flags it as worth a dedicated directional run before leaning on it hard.

Q4: 8 GCDs are schedulable per node (each of the 4 MI250X packages exposes two Graphics Compute Dies, and the GCD is what ROCm and Slurm schedule). A rank-per-GPU job should launch 8 ranks — a 4-rank launch built from the "4x MI250X" diagram idles half the accelerator.

Q5: Nothing is wrong. A single rank per node crosses only one of the four Slingshot NICs, and per-link bandwidth is ~22.6 GB/s; the 100 GB/s figure is a whole-node injection spec. Spreading ranks across the four NUMA domains (-c 14 gives one rank per domain, one NIC each) scales linearly to 90.3 GB/s ≈ 90% of spec.

Q6: The declared map puts GCD 0 and GCD 1 on NUMA 3 — but I have low confidence in this. gpu.numa_affinity is in the Unverified section, marked "unfalsifiable here" and confirmed by no measurement; it rests on the same vendor whose CPU distance table the briefing contradicts. So: nominally GCD 0 and 1, not measurement-backed.

Q7: L1 ≤ 32 KB (~1.1 ns), L2 ≤ 512 KB (~3.4 ns), L3 ≤ 32 MB (~10.9–13.3 ns), DRAM ~87–89 ns. L3 is shared per L3 group ("CCD"/CCX); the eight OS-reserved cores (one per group) imply 8 L3 groups of 8 cores each sharing one 32 MB L3. One caveat: the cache section labels these "four CCDs" while the reserved-core evidence points to eight L3 groups, so the exact group count is slightly inconsistent in the briefing even though the 32 MB per-group size is solid.

Q8: Not necessarily — a success return here does not mean you have huge pages. THP is set to never and the hugetlb pool is exhausted (Total 4, Free 0), so both normal paths fail silently: the allocation succeeds but is backed by 4K pages. Verify with smaps, not the madvise return; to actually get 2M pages you must load craype-hugepages2M, which works by relinking the binary.

Q9: Yes, dramatically — 32 MiB with random access is the single worst case for page size on this node. It still fits in L3, but 4K pages need 8192 PTEs, far past TLB reach, so every access pays a page walk that itself goes to memory: latency is ~13.3 ns on 2M pages versus ~32.2 ns on 4K, a 2.4× penalty. The trap is that it peaks exactly where the working set still fits in cache, where you wouldn't look for it.

Q10: No. 98.3% of peak bandwidth is available at the knee at 2.7× lower latency (43,752 MB/s @ 234 ns vs peak 44,521 MB/s @ 832 ns). Tuning to fully saturate buys 1.7% more throughput at the cost of 2.7× latency — sit at the knee, not the peak.

Q11: It depends on message size. Device buffers beat host staging above the crossovers — bandwidth crossover at 16 KB, latency crossover at 256 KB — and at 4 MiB device buffers win by ~+5.5% bandwidth / +5.9% latency. Below ~64 KB host is 12–14% better. Production GPU HPC and LLM training move megabytes and sit well above both crossovers, so device buffers; note the ~5.5% lives entirely in the NIC-to-memory hardware path, not in enabling GPU-aware MPI (which costs ~0 by itself).

Q12: Host staging. A 16 KB halo is a latency-bound ping-pong that pays the fixed cost every round trip, and the latency crossover isn't reached until 256 KB — at 16 KB you're below it and also inside the small-message penalty region (12–14% worse below 64 KB). The bandwidth crossover at 16 KB doesn't help you because a halo exchange isn't a streaming benchmark.

Q13: The declared map puts GCD 0's local domain at NUMA 3, so nominally place the buffer on NUMA 3 — but confidence is low, for the same reason as Q6. This is the Unverified gpu.numa_affinity claim, taken on faith from the vendor whose CPU SLIT is contradicted elsewhere in this briefing; the effect, if real, is below 8% GPU-latency variance and hasn't been measured. If it matters, measure it (e.g. move_pages-verified) rather than trusting the map.

Q14: The briefing does not cover this — I can't say. The loaded-latency/knee probe sweeps read-only traffic only; read/write mix is explicitly listed under "Not measured," with the note that write traffic saturates differently. So I have no data on whether write-heavy traffic behaves the same.

S1 — Whole node, maximum throughput:

srun -N1 -n8 -c7 --gpus-per-node=8 --gpu-bind=closest ./qmcpack diamond_vmc.xml
# env:
OMP_NUM_THREADS=14
OMP_PROC_BIND=spread
OMP_PLACES=cores
8 ranks so every one of the 8 schedulable GCDs is engaged (a 4-rank job idles half the accelerator). -c 7 × 8 = 56, using exactly the 56 usable cores and stepping over the 8 OS-reserved cores that would make -c 8/-c 64 fail. OMP_NUM_THREADS=14 uses both SMT threads on each of a rank's 7 cores, reproducing the 112-walker configuration that already beat the starved single-rank run (68.0 s vs 155.8 s). One honest caveat: --gpu-bind=closest relies on the unverified GPU↔NUMA affinity map (Q6/Q13) — if you want to remove that risk, replace it with an explicit --gpu-bind=map_gpu:... once you've confirmed the mapping in an allocation.

S2 — Four GCDs only:

srun -N1 -n4 -c14 --gpu-bind=map_gpu:1,3,5,7 ./qmcpack diamond_vmc.xml
# env:
OMP_NUM_THREADS=14
OMP_PROC_BIND=spread
OMP_PLACES=cores
Pick one GCD from each of the four NUMA domains (declared map: {4,5}/{2,3}/{6,7}/{0,1}) so the four ranks spread one-per-domain, one-NIC-each, matching the -c 14 layout the NIC policy wants. I chose the odd dies (1,3,5,7) because gpu.die_parity (medium confidence, one node) shows odd GCDs have markedly lower and steadier host-memory latency — sensible for QMCPACK's host-driven offload — but that's medium confidence, so it's a tie-breaker, not a load-bearing choice. -c 14 lets the 4 ranks still use all 56 usable cores (14/domain), keeping walker count high; expect roughly half the whole-node throughput since you have 4 of 8 GCDs.

S3 — One NUMA domain:

srun -N1 -n2 -c7 --gpu-bind=map_gpu:2,3 ./qmcpack diamond_vmc.xml
# env:
OMP_NUM_THREADS=14
OMP_PROC_BIND=spread
OMP_PLACES=cores
One NUMA domain gives you 14 usable cores (28 hardware threads) and its 2 local GCDs, so 2 ranks × 7 cores × 14 threads. I picked NUMA 1 (GCDs 2,3) rather than NUMA 0 on purpose: per cpu.system_interference (declared, untested), NUMA 0 uniquely hosts both NVMe controllers, the management NIC, and a DMA channel, so it carries interrupt/DMA jitter the other domains don't. Relative to the whole node you have 2 of 8 GCDs and 14 of 56 cores — about one-quarter of the resources, so expect roughly 4× the wall-clock. Two caveats: which GCDs are actually "local" to the domain is the unverified affinity map, and the NUMA-0 avoidance rests on a declared-but-untested device-locality claim.

S4 — Memory-bound preprocessing (CPU-only, ~32 MiB/thread working set):

srun -N1 -n1 -c56 ./preprocess     # (or -n4 -c14, one rank per NUMA domain)
# env:
OMP_NUM_THREADS=56
OMP_PROC_BIND=spread
OMP_PLACES=cores
# ensure NUMA-local first-touch allocation across all 4 domains
Spread threads across all four NUMA domains with first-touch local allocation to get ~4× single-domain bandwidth (~44.5 GB/s/domain), and target the bandwidth knee, not the peak (Q10): near-peak bandwidth costs 2.7× less latency. The surprise is the 32 MiB working set: that's the exact peak of the 4K-page latency cliff (2.4×, Q9), so a developer's instinct is "get huge pages" — but (a) huge pages fail silently on this node unless the binary is relinked with craype-hugepages2M (Q8), and (b) for a streaming bandwidth-bound phase page size barely matters anyway (107,765 vs 107,342 — the penalty is a latency effect that sequential reads amortize). So if the access is truly streaming, don't spend effort chasing huge pages; if it's actually random-access at 32 MiB, you'll hit the 2.4× cliff and the relink genuinely helps. One more: keep I/O-heavy work off NUMA 0 if you can, for the same device-locality reason as S3.
