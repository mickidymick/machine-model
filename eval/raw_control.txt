PART 1 — QUESTIONS ABOUT THE MACHINE

Q1: 56 cores usable, and the maximum valid srun -c is 56. hwloc reports 112 allowed PUs of 128 (indices 112–127 reserved) = 56 usable cores of 64; the vendor "64 cores" diagram is wrong here. The core-count-ceiling note confirms -c 64 is rejected and -c 56 is the ceiling, because one core per L3 group (0, 8, 16, 24, 32, 40, 48, 56) is OS-reserved.

Q2: All six pairs are equivalent — every remote hop is 12 (1.2× the local value of 10) in the ACPI SLIT. There is no cheapest or most expensive pair; 0-1, 0-2, 0-3, 1-2, 1-3, 2-3 all cost the same by the reported distance matrix.

Q3: As reported, yes, it is symmetric (12 in both directions). But note the SLIT/hwloc distance matrix is structurally one scalar per pair, so it cannot represent asymmetry even if the hardware had some — the symmetry is partly an artifact of the data format, not a measurement that ruled asymmetry out.

Q4: 8 — the 4× MI250X present as 8 GCDs (GPU[0]..GPU[7] / card0..card7), and Slurm schedules those 8 GCDs as the GPU devices. A rank-per-GPU job should launch 8 ranks, one per GCD.

Q5: Nothing is wrong. The 100 GB/s injection spec is the whole-node figure across all 4 Slingshot NICs (one per NUMA domain), so one rank crosses a single NIC ≈ 25 GB/s — your 24 GB/s matches. The one-rank-one-nic note is explicit: spread ranks across the four NUMA domains (e.g. -c 14 → one rank per domain) to engage all four NICs.

Q6: GCD 0 and GCD 1 are attached to NUMA domain 3 (per rocm-smi --showtoponuma, corroborated by hwloc).

Q7: L1 = 32 KB, L2 = 512 KB (both per-core), L3 = 32 MB shared per CCD. On this Zen3 part the CCD's L3 is shared across that die's 8 physical cores (7 usable after the one reserved core per L3 group).

Q8: No — success does not prove you have huge pages. The huge-pages-fail-silently note is exactly this trap: THP can be [never] and the hugetlb pool empty (Total 4 / Free 0) while the normal paths, including the madvise return, report success. Verify by inspecting smaps for the actual page-backing, and on Frontier get huge pages by loading craype-hugepages2M (relink, not a runtime flag).

Q9: Yes, page size can still matter, but for the TLB, not the cache. Fitting in 32 MB L3 removes cache misses, but random access over 32 MiB with 4 KB pages needs ~8192 distinct translations, which typically overruns the L2 TLB and triggers page walks; 2 MB pages cut that to ~16 entries. Caveat: the descriptor gives no TLB sizes, so this is architectural reasoning, not something measured on this node.

Q10: I can't give you a bandwidth target — the descriptor states plainly that no performance measurements were taken, and two measured operational notes are explicitly withheld. Whether saturation tuning pays off depends on whether your kernel is actually DRAM-bandwidth-bound, which this data can't tell you. The one machine-specific caveat I can give: NUMA 0 carries extra device/DMA traffic (see Q13/S4), so it is not a symmetric bandwidth target.

Q11: The descriptor contains no data on GPU-direct vs host-staged transfer on this node, so I can't give a machine-specific answer or crossover point. From general GPU-aware-MPI practice (not this descriptor): large messages usually favor sending directly from device buffers (RDMA avoids the copy), while very small messages are latency-bound and host staging is sometimes competitive — so yes, the answer generally depends on size, but I'd treat the crossover as unknown here and measure it.

Q12: I don't have the measured device-vs-host crossover for this machine, so I can't answer definitively. 16 KB is past the tiny-message latency floor where host staging tends to win, so device-direct via GPU-aware MPI is a reasonable default to try — but that's general reasoning, and I'd confirm with a quick sweep rather than state it as fact for this node.

Q13: Put it on NUMA domain 3 — GCD 0 is physically attached there. High confidence: two independent sources agree (rocm-smi --showtoponuma and hwloc os=cardN → NUMANode), both listing all eight devices with the same mapping.

Q14: I don't know — the descriptor has no write-bandwidth figures, and this is plausibly one of the two withheld measured notes. Write-heavy traffic often does not mirror read bandwidth on these parts, but I have no numbers for this node and won't invent one; measure it if it matters.

PART 2 — CONFIGURING QMCPACK

S1 — Whole node, maximum throughput

module load craype-hugepages2M        # verify huge pages via smaps, not madvise
export OMP_NUM_THREADS=14
export OMP_PROC_BIND=spread
export OMP_PLACES=threads
export OMP_TARGET_OFFLOAD=MANDATORY
srun -N1 -n8 -c7 --threads-per-core=2 --gpu-bind=closest ./qmcpack diamond_vmc.xml

8 ranks because all 8 GCDs must be engaged — the single-rank starvation cost you 7× throughput. -c 7 × 8 = 56, exactly the usable cores (the 8 reserved L3-group cores are excluded automatically); --threads-per-core=2 + OMP_NUM_THREADS=14 gives 112 threads total → 112 walkers, matching the 68.0 s measured configuration. --gpu-bind=closest binds each rank to its NUMA-local GCD (2 ranks per NUMA domain), keeping walker data on local memory and spreading traffic across all four NICs; craype-hugepages2M because the huge-page request otherwise fails silently.

S2 — Four GCDs only

export OMP_NUM_THREADS=14
export OMP_PROC_BIND=spread
export OMP_PLACES=threads
export OMP_TARGET_OFFLOAD=MANDATORY
export ROCR_VISIBLE_DEVICES=4,2,6,0    # one GCD per NUMA domain: 0,1,2,3
srun -N1 -n4 -c14 --threads-per-core=2 --gpu-bind=closest ./qmcpack diamond_vmc.xml

Pick one GCD from each NUMA domain (GCD 4→N0, 2→N1, 6→N2, 0→N3) rather than four from two domains, so every rank has local memory and a distinct Slingshot NIC — this maximizes memory and network balance under the 4-GCD cap. 4 ranks × 14 cores = 56 cores, OMP_NUM_THREADS=14 × --threads-per-core=2 = 28 threads/rank → 112 total threads/walkers, so you keep full CPU/walker occupancy but on half the GPUs (expect the GCDs to be the bottleneck). --gpu-bind=closest with one rank per domain binds each to its co-located GCD.

S3 — One NUMA domain

export OMP_NUM_THREADS=14
export OMP_PROC_BIND=spread
export OMP_PLACES=threads
export OMP_TARGET_OFFLOAD=MANDATORY
srun -N1 -n2 -c7 --threads-per-core=2 --gpu-bind=closest --mem-bind=local ./qmcpack diamond_vmc.xml

One NUMA domain gives you 14 usable cores and 2 GCDs (e.g. NUMA 3 → GCD 0 and 1), so 2 ranks, one per GCD, -c 7 each (7 cores × 2 HWT = 14 threads/rank, 28 threads total). Relative to the whole node this is ¼ of the GCDs, ¼ of the cores, and a single NIC — so roughly ~4× less sampling throughput (order of ~1/4 the walker rate), i.e. a whole-node-equivalent job would take on the order of 4× longer. --mem-bind=local keeps allocation in-domain, which matters more here since you have no bandwidth to spare.

S4 — Memory-bound preprocessing (CPU-only, ~32 MiB/thread)

module load craype-hugepages2M        # then confirm backing in smaps
export OMP_NUM_THREADS=56
export OMP_PROC_BIND=spread
export OMP_PLACES=cores
srun -N1 -n1 -c56 --threads-per-core=1 ./preprocess

32 MiB/thread exceeds the 32 MB per-CCD L3, so this is genuinely DRAM-bandwidth-bound: use 56 threads, one per physical core, no SMT (a second thread per core adds no memory bandwidth), spread across all four NPS4 memory controllers with first-touch/local allocation. Load craype-hugepages2M and verify via smaps, since the working set will hammer the TLB and the huge-page request otherwise fails silently.

The surprise: NUMA 0 is not symmetric with the others. Although SLIT reports all four domains equidistant and NPS4 looks uniform, NUMA 0 alone hosts the management NIC, both NVMe drives, and the DMA channel — so its memory controller carries extra interrupt/DMA load and a bandwidth sweep will show NUMA 0 threads lagging the other three. And if your preprocessing is write-heavy, don't assume it saturates like reads — the descriptor gives no write-bandwidth number (see Q14), so measure it.
