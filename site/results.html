Does the artifact change what a model knows about the machine?

Two arms, one model (Claude Opus 4.8, effort High), separate fresh sessions, 14 questions with checkable answers. Both arms generated from the same descriptor, so the single difference between them is measurement.

The result

Question categorycontroltreatment
Docs sufficient5/55/5tie — the validity check
Docs misleading1/33/3
Measurement only1/44/4
Neither knows1/22/2declining is the right answer
Confidently wrong10incorrect, stated as fact

The tie on “docs sufficient” is the number that makes the rest trustworthy. Five questions the documentation answers correctly, and both arms get all five. If the measured arm had won there too, the control was built to lose and nothing else on this page would mean anything.

Where the difference actually is

It is not that the control knows less. It is that the control cannot tell the difference between a fact that is missing and a fact that is wrong.

Where the documentation says nothing, the control hedges correctly. On the questions no source answers — the loaded-latency operating point, the host-versus-device crossover, the read/write mix — it declined cleanly every time. That is good behaviour, and it is why the honest reading is not “models don't know machines.”

Where the documentation is wrong, it repeats the error as fact. Asked to rank the six NUMA domain pairs by crossing cost:

answer
control“All six pairs are equivalent… it’s a flat tie.”
treatment“They are not equivalent” — then all six pairs, in order, with the three-tier structure

The control is not guessing. It is reporting the ACPI SLIT accurately. The SLIT is wrong. Hedging protects a model from missing information but not from false information — and the control’s own good behaviour everywhere else is what proves it.

The calibration question

One question has no verified answer on either side. The right response is to say so. We asked where to place a host buffer for GCD 0, and how confident it was.

answer
control“NUMA domain 3, and I’m highly confident — backed by two independent agreeing sources.”
treatment“Declared answer: NUMA domain 3. My confidence is low — this is exactly gpu.numa_affinity, which is unverified… I wouldn’t state it as a measured fact.”

Same answer, opposite calibration. Both probes we ran against that claim failed to discriminate, so the artifact records it as unfalsifiable_here — and the briefing’s Unverified section survived contact with a direct question instead of being promoted into a recommendation. That was the property we were least sure would hold.

What we got wrong, and fixed

Three of these were caught by scoring our own experiment. They are on this page because a result you cannot see the failure modes of is not a result.

ProblemEffect
The control was over-supplied. Five of six “operational notes” were our own discoveries, including NIC scaling measured that same afternoon. The control was running on our results relabelled as documentation. Pitfalls now carry provenance, and only documented ones reach it.
The scoring rubric hid most of the result. Counting a hedge as success everywhere scored “honest but no answer” the same as “correct.” Both arms tied 4/4 on measurement-only questions where one answered and the other declined. A hedge now counts only where declining is correct. Control moved 11/14 → 8/14.
Promoting a finding deleted it. gpu.die_parity moved from flagged to observations; the renderer knew only about flagged. The finding vanished from the briefing with no error, leaving an open question referring to a result no reader ever saw. The treatment numbers above are a lower bound.

Both arms are being re-run against the corrected inputs. The first run is archived rather than discarded — the gap between an over-supplied control and an honest one is itself a measurement.

What this does not show

One model, one effort level, one session per arm.Not blinded, not replicated across models. A shape, not a study.
The control is a document we curated.A real user has an assistant with shell access that gathers what it thinks to ask for. That arm is the honest baseline and has not been run.
No application was actually run.This measures what a model knows, not whether the resulting configuration is faster. That is the QMCPACK experiment, and it needs machine time.
One machine, largely one node.Whether any of this generalises is what Tuolumne and Aurora are for.
