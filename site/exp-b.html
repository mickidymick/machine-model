Two experiments · Frontier · 2026-08-10 and 2026-08-13

It changed the answers. Then it made the code slower.

Experiment A asked whether a measured machine artifact changes what a model says. It does, decisively — but only against measurement, because a session with nothing but web search matched a curated topology document exactly. Experiment B asked whether that converts into a faster run. It did not. The agent without the artifact produced the faster configuration, by 2.9%, at p = 6.3×10−8.

Experiment A — the artifact changes the answers

Fourteen questions with checkable answers, three fresh sessions, one arm each. web was told only the machine’s name and had search. declared got a curated document built from what the machine says about itself — hwloc, the node diagram, the ACPI tables. measured got our briefing.

Web search matches the curated document, exactly

web and declared score identically in every category. Everything we hand-assembled from the machine — the non-obvious NUMA ↔ GCD map, the 56-core low-noise reservation, even Slurm’s -S 8 — a session told only “you are on Frontier” found in the OLCF User Guide. Frontier is documented well enough that free search reproduces a curated topology summary. So the curated document buys essentially nothing, and the only gap this project may claim is declared → measured.

The result stated properly: hedging protects a model from missing information but not from wrong information. Where nothing is published, every arm declined cleanly. Where the ACPI SLIT is published and wrong, they repeat it as fact — and the one confidently wrong answer in the whole evaluation came from the tidy curated document, not from search.

Experiment B — but it did not make the code faster

Two agents, the same benchmark source, the same fixed problem, the same one-node budget. They differed in one file.

The ladder

Floor is ZeroSum’s naive default reproduced — one node, 8 ranks, 7 OpenMP threads, no -c. Ceiling is hand-tuned from every claim this project has measured. 5 configurations × 10 interleaved passes, 50 runs, 0 failures.

The four fast configurations, in detail

Axis does not start at zero — this is a zoom on the 27–29 s band of the chart above, where the arm difference lives.

The pre-registered mechanism did not fail to help. It hurt.

The whole experiment was built around huge pages. Our briefing records a 2.4× page-size penalty at a ~32 MB working set, and craype-hugepages2M works by relinking, so it must be a build-time decision. That was the predicted source of the entire effect — in the treatment arm’s favour.

Isolated by taking the treatment configuration and removing that one module, leaving everything else identical: huge pages cost 0.76 s (2.67%), p = 3×10−10 — 96% of the entire arm gap. Strip them and the treatment arm becomes statistically indistinguishable from the control (27.69 vs 27.66 s, p = 0.35).

n = 10 per configuration, interleaved in one allocation. The control and the huge-page-free treatment build are byte-identical binaries, so the only thing separating them is the runtime environment — and it measures as nothing.

Why: the number was right, the regime was wrong

The control considered and rejected the module, and said why:

the hot kernel streams 64 contiguous ~12 KB coefficient chunks per spline evaluation, so page walks overlap with the DRAM traffic they precede — this code is bandwidth-bound, not TLB-latency-bound, so the payoff is small.

It was right, and it understated its own case. Our 2.4× is a correct measurement — taken with a pointer-chase, dependent random access. miniQMC streams. Outside its regime the number did not merely fail to apply: it inverted. A measured 2.4× benefit became a measured 2.7% penalty.

A plausible mechanism, offered as hypothesis rather than result: first-touch granularity. With 4 KB pages each thread’s slice of the ~19 MB determinant matrices lands on its own NUMA domain exactly. With 2 MB pages a single page can span data first-touched by threads on different domains, so placement coarsens and some reads go remote. That would bite precisely this code — 8 ranks × 7 threads, all relying on first touch, on a four-domain node. Testing it is future work.

And the briefing said so itself

Line 17 of the document the treatment arm was reading:

Conditions are part of every number. A latency measured on 4K pages, or a bandwidth measured across one of four network links, does not generalise to other conditions. The conditions are stated; carry them.

The caveat was present, in context, and the misapplication happened anyway. Stating conditions in prose is not sufficient to stop a number being used outside the regime it was measured in. That is a design finding about measured-machine artifacts, not merely a null result.

Our own hand-tuned reference was beaten

The ceiling encoded our measured NUMA claims as 4 ranks × 14 threads, one per domain. Both agents independently chose 8 × 7 on L3 boundaries, and both beat it. The treatment arm explicitly considered 4 × 14 — its own choice in an earlier round — and rejected it: one core per L3 group is OS-reserved, leaving exactly 7 usable per CCD across 8 CCDs, so 8 × 7 is the only geometry confining a rank to a single L3 and a single NUMA domain.

The ceiling is also the noisiest configuration in the set (sd 1.67% against 0.19–0.67% elsewhere).

The harness is measuring what it should

Floor → ceiling spans 2.09×, against ZeroSum’s published 2.33× (63.67 → 27.33 s) on the same benchmark and the same machine, with our floor reproducing their baseline shape exactly. Equal work was verified on all 50 runs — 56 walkers, recovered independently from ranks × walkers and from FOM × time / nelec3.

Method follows their section 4.1: n = 10 per condition in one allocation, interleaved in rotating order, decided by a Welch t-test rather than a ratio of single runs.

How the attribution was established

Five one-knob configurations, each the treatment arm with exactly one change. OMP_PLACES, --distribution, BLAS linkage and craype-x86-trento all measured null; removing huge pages recovered 96% of the gap. The compiler-target hypothesis was killed for the cost of one objdump: both binaries contain identical instruction counts (2779 FMA, 19521 AVX2), so codegen was never the difference.

One correction worth recording: the BLAS knob produced a byte-identical binary, so that comparison never varied anything and its null is not evidence about BLAS.

What is still not established

The first-touch mechanism above is a hypothesis, not a measurement. And this is one benchmark, one machine, one configuration per arm — not “measured artifacts make code slower.” A pre-registered follow-up on XSBench, whose random binary search is the access pattern our 2.4× was actually taken under, tests whether the same fact helps when the regime matches.

Reading the two together

Experiment A is not undone by Experiment B. They answer different questions and the answers are consistent: the artifact reliably changes what a model says, and that did not convert into a faster run on this benchmark. The mechanism connecting them is the same in both directions — a fact is only as good as the regime it was measured in, and neither a published source nor our own measurement carries that regime with it by default.

Where a published number is wrong, A shows the artifact fixes it: 3/3 against 1/3 on the misleading-docs questions. Where a number is right but taken under a different access pattern, B shows the artifact actively misleads. Those are the same defect seen from two sides — context that travels separately from the number it qualifies.

And the honest deflation, which belongs in both: on a machine as well documented as Frontier, plain web search already reproduces a curated topology summary. The artifact’s value was never in restating what OLCF publishes.

What this supports

  1. Against measurement-only and misleading-docs questions the artifact wins decisively; against a well-documented machine, web search matches a curated declared summary exactly.
  2. On this workload the artifact’s contribution to runtime was negative and significant, and 96% of it is attributable to a single measured fact applied outside its regime.
  3. The failure is regime mismatch, not bad data. Every number in the briefing is correct — and outside its regime the number inverted its sign, which is worse than being useless.
  4. The briefing’s own conditions field did not prevent the misuse.
  5. A control with no machine document reasoned to the better configuration from the source code, and beat our hand-tuned reference.

The design step this points to: a measured artifact should carry the access pattern under which each number was obtained as a first-class, matchable field — something a reader must reconcile against its own workload — rather than as prose it is asked to honour.

What is actually in the artifact

Sixteen claims, one schema, the same questions asked of every machine. Each carries a verdict — how the machine’s own description held up against measurement. Empty slots are expected and are part of the record.

confirmed4

The machine tells the truth. This is the control — without it, “firmware is unreliable” would be an unfalsifiable complaint.

  • cpu.cache_hierarchySets blocking targets. Also calibrates our own latency tool against known hardware.
  • numa.domain_countThe unit of memory placement. Everything downstream assumes it.
  • gpu.interconnect_costDecides which device pairs should hold communicating partners.
  • gpu.memory_hierarchyKernel blocking targets, and validates the GPU probe.
misleading3

Declared sources disagree with each other. A user who runs the right tool gets the right answer; one who reads the vendor diagram does not.

  • cpu.core_inventorySets -c and ranks per node. Wrong either wastes the allocation or gets the job rejected.
  • gpu.device_inventoryPackages vs schedulable GCDs — a standing source of 2× errors in rank counts.
  • net.nic_inventoryDecides whether a measured bandwidth is per-link or per-node. A factor-of-N error either way.
contradicted3

The machine states something false. This is the category the project exists for.

  • numa.distance_matrixLinux exposes this through numa_distance(). Placement, migration and binding tools all read it.
  • numa.symmetryDirection matters here, and a scalar distance cannot express that at all — not miscalibrated, structurally insufficient.
  • mem.page_backingSilent failure invalidates every latency measured afterwards, and the result still looks plausible.
undeclared4

Nothing published answers these. Measurement is the only source — and the only place the artifact is not competing with a search engine.

  • cost.page_size_penaltyNot a constant: zero while the TLB covers the working set, spikes when TLB reach fails, then settles. This is the one that inverted in Experiment B.
  • cost.loaded_latency_kneePeak and usable bandwidth are different operating points, often far apart.
  • cost.host_device_transferDevice vs host staging changes sign with message size. One measurement gives the wrong universal answer.
  • cost.contention_sensitivityCharacterising an idle node describes a machine nobody runs on.
unfalsifiable here1

We probed it and the probe could not discriminate. Recorded as such rather than quietly dropped.

  • gpu.numa_affinityDrives --gpu-bind=closest and every host-buffer placement. Two probes failed to separate the domains.
untested1

Known to matter, not yet measured. Listed so the gap is visible rather than implied.

  • cpu.system_interferenceThe question binding tools exist to answer: which resources to keep an application off.

Declared values are never overwritten; measured values sit alongside them. Overwriting would destroy the evidence that anything reading numa_distance() is wrong, which is the finding.
